## ARCHITECTURE CHANGES
================================================================================

### Progression System

OLD (ELO-based):
  • User global_elo_rating: float (800–2000 scale)
  • Per-skill elo_rating: float (800–2000 scale)
  • Confidence tracking via trust_score: float (0–1)
  • Difficulty computed as: 800 + (depth * 100)
  • Level display: frontend conversion eloToLevel() using fixed thresholds

NEW (XP + Levels):
  • User total_xp: int (0–1000+), current_level: int (1–6)
  • Per-skill xp: int (0–1000+), level: int (1–6)
  • Level derived from XP via compute_level_from_xp()
  • Difficulty as required_level: int (1–6, computed from topological depth)
  • Backend returns XP/level directly (no frontend conversion)

### Course Filtering & Unlocking

OLD:
  • get_adaptive_skill_score() computed ELO-distance band
  • Recommend endpoint returned user_elo, filtered by confidence
  • Resources ranked by ELO-distance heuristic

NEW:
  • recommend.py filters: required_level ≤ user_level + 1
  • Simplistic integer-based level progression (easier to understand)
  • Resources ranked by quality_score + is_primary (deterministic)

### API Return Types

OLD:
  • user_elo: float
  • global_elo_rating: float
  • elo_rating: float
  • trust_score: float
  • difficulty_level: float (800–2000)

NEW:
  • user_xp: int (0–1000)
  • user_level: int (1–6)
  • total_xp: int
  • current_level: int
  • xp: int (per-skill)
  • level: int (per-skill)
  • required_level: int (1–6)

### XP Awarding

  • Completion: depth * 20 + 10 (min 10 XP per course)
  • Quiz ≥80%: full XP | ≥50%: half XP | <50%: 0 XP
  • Both User and UserSkill rows updated atomically
  • Level recalculated after every award

### Cold-Start UX

NEW:
  • DataLoadingState wrapper component
  • Skeleton screens suppress rendering during load
  • Staged messaging: skeleton only → "Waking up..." → "Preparing..."
  • fade-in animation at ≥5s elapsed

DATA FLOW:
  1. User sends message in AIMentorPage textarea → sendChatMessage(message)
  2. Frontend: sendChatMessage() → POST /chat via fetchWithAuth() + Clerk JWT
  3. Backend /chat endpoint receives {message: string}, validates Clerk auth
  4. Router calls Gemini API with message + TOOL_DECLARATIONS in initial payload
  5. Gemini responds with tool_calls (or text if no tools needed)
  6. For each tool_call:
     a. Router extracts tool_name + args
     b. If tool_name in USER_ID_TOOLS: override args["user_id"] = authenticated_user_id (security)
     c. Call TOOL_REGISTRY[tool_name](**args)
     d. Append result to conversation history
  7. Loop max 5 rounds until Gemini responds with no tool_calls
  8. Return ChatResponse{reply: final_text}
  9. Frontend receives reply, appends to messages[], setLoading(false)

SECURITY CONSIDERATIONS:
  • Router always overrides user_id in tool calls — prevents LLM from querying other users
  • Clerk JWT validation required for /chat endpoint
  • Tools fetch only current user's data (user_id forced by router)
  • MCP tools open/close DB sessions (stateless, safe for concurrent requests)

GEMINI CONFIGURATION:
  • API Key: GEMINI_API_KEY env var (required)
  • Model: gemini-3-flash-preview (configurable via GEMINI_CHAT_MODEL)
  • Temperature: 0.7 (creative but grounded)
  • Max output tokens: 1024
  • System prompt: Instructs model to use tools before answering

KNOWN LIMITATIONS:
  • Max 5 tool-call rounds per request (prevents infinite loops)
  • 60s timeout per request (Gemini latency + tool execution)
  • Tool errors caught and returned as {error: str} in response
  • LLM cannot modify data (all tools are read-only queries)
